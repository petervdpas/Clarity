## Design

### Folder and file parts with options (asked 2026-11-18, not built)

The user's words: "make a proper folder and file part with options (allowed file types and such)". Their answers:
- The file part holds "Both, by its bind": bound to a `file` field it is the record's file, as now; bound to a path it is a file's path on disk. Both shapes take the same options.
- The `...` buttons of both parts open the system's own dialogs, with filters: "os dialog with filters!!!!!" (2026-11-18; an earlier answer of "Clarity's own browser" was taken back). The conflict below stays as it is: generated apps open the system's file and folder dialogs.
- Options, each off by default: `extensions` on a file part (the files its dialog offers, `"*.png *.jpg"`), `start folder` on both parts (where the dialog opens while nothing is chosen), `new file` on a file part (a file that is not there yet may be named, to save to). `hidden` is no option of the parts: the Linux portal cannot be told to show hidden files, so it would not work alike on every system; it stays an option of a folder field for what code lists.
- Web apps: "browse the local filesystem... how the hell can that be the server!!!!". The folder or file is the person's own, on the machine the browser runs on.

Answered 2026-11-18:
- Web apps: the `...` button opens the browser's own picker and the chosen files go to the program, uploaded ("yes that acceptable"). A web page reaches local files only that way and gets their contents, never a path.
- Names: "that sounds backward!! why isnt record called record?": `file` is to mean a file on disk, and the record's file gets a name of its own.
- Options in the markup "is fine as long as they can be set by options in properties of part!": every option is in the part's properties in the designer.

- The record's file is a `blob` ("yes, blob"): its bytes and name, in the database or a file store. `file` becomes a file's path on disk. Projects with a `file` field of today are rewritten to `blob`.
- `extensions` on a `blob` or `file` field refuses a file of another type put in by code too ("refuse wrong types"), as a folder field refuses writing one.
- Option names in the markup: `extensions`, `startFolder`, `newFile`, each also in the part's properties. Spec BUILT 2026-11-18 (`crates/clarity-spec/tests/spec/dialog_options.rs`).

Steps:
1. Rename the type `file` to `blob` everywhere (spec, generators, IDE, manual, examples). BUILT 2026-11-18: `FieldType::Blob`, the keyword `blob`; a field or migration line written `file` is refused with "a file kept in the record is a 'blob' now: write 'manual: blob'" (`parser.rs` `parse_field_typed`, test `blob_fields.rs`), so the person rewrites it; there is no quick fix for diagnostics. The runtimes needed nothing: they never read the type's word. The entity editor now offers a store for a blob too, not only an image.
2. The system's dialogs take the options. BUILT 2026-11-19: `Ask.folder` opens each dialog in its start folder (zenity `--filename`, kdialog's start path, osascript `default location`, the portal's `current_folder`, Windows `SetFolder`); `FilePicker` takes `start` in its three dialogs; the folder part opens in the folder it holds, else its `startFolder`; the file part gives its `extensions` as the filter (`files::filter_of`) and its `startFolder` (`files::start_folder`, relative to the program's folder) to Choose and Save a copy. Tests: `runtimes/rust-ui/tests/hosts/desktop_host.rs` (every system), `tests/inputs/inputs_file.rs`, `inputs_folder.rs`; `windows.rs` type-checked for x86_64-pc-windows-msvc only, not run on Windows. Manual `parts.input.md`; designer properties Extensions, Start folder, New file. `newFile` does nothing on a blob part (a blob needs a file that is there to read): it takes effect with step 3's `file` path field, and the checker should then refuse it on a blob.
3. The new `file` type and its part, on every stack; the options in the parts' properties in the designer. Shaped after Avalonia's storage provider ("yes, do it the avalonia way", 2026-11-19): Clarity.UI's `FilePicker` takes one options object (title, file types, start folder, suggested name), as `FilePickerOpenOptions` does, and gives storage items (`StorageFile`, `StorageFolder`: a name, read and written, a path only where the system has one), as `IStorageFile` does; each host gives its own (the system's dialogs on the desktop, the page's file access in a browser). A `file` field is kept as its path on the desktop; in a web app it is the file the person picked (step 5). Avalonia's own `IStorageProvider` is C# only, so Clarity.UI follows its shape rather than calling it. BUILT 2026-11-19: Clarity.UI's `StorageProvider` (was `FilePicker`, renamed as Avalonia names its one provider) with `open_file`, `save_file` (where; nothing written), `write`, `open_folder`, each taking `PickerOptions` and giving a `StorageFile` or `StorageFolder` (`runtimes/rust-ui/src/files.rs`); the desktop, the page, the headless driver and the tests give theirs. `FieldType::File` is a path kept as text, everywhere `folder` is (spec, five generators, db, mappings); a setting may be a `file`. A file part bound to a `file` field is the path part (`parts/inputs/path.rs`, `PathPart`, shared with the folder part), choosing with the open dialog of its extensions or, with `newFile`, the save dialog, opening beside the file it holds else in its start folder; bound to a blob it stays the record's file. The checker refuses `new file` on a blob. Tests: spec `file_paths.rs`, `dialog_options.rs`; Clarity.UI `inputs_file.rs`; the everything fixture holds `Album.scan: file` and builds in Go, C, C++ and Rust (C# not run: the local native libraries were older than their Rust and need DevTools builds). A table shows a `file` column as text and does not edit it. Projects written for Clarity 1.6 with `file` fields read them as paths now: no project outside the repository had one (checked 2026-11-19).
4. Refusing wrong types in code for `blob` and `file`, on every stack (conformance). BUILT 2026-11-19. The user's words: "in the extentions option for file/folder browse I want to be able to give a list like '.png, .jpg, .gif' or '*.* for all extentions'", "hidden is a special boolean", "I'm talking about the part settings in the designer". Extensions are written as that list everywhere (fields and parts; `*.md *.csv` still reads; `crates/clarity-spec/src/files.rs` `patterns_of`, `written_of`); `extensions` and `hidden` are options of fields of type folder, file and blob, and of both parts, each with its designer property (Extensions with the placeholder `.png, .jpg, .gif or *.* for all`, Hidden a checkbox). A blob or file field that names extensions refuses a file of another type, a hidden one without `hidden`: the checker on a path written in code; every runtime's `check_file_type` (R `files::check_file_type`, Go `CheckFileType`, C `clarity_check_file_type`, C++ `check_file_type`, C# `Db.CheckFileType`; conformance `fieldFiles`), run by each generator before code sets the field (`clarity-gen` `file_check`; test `crates/clarity-gen/tests/gen/file_checks.rs`); Clarity.UI's file part and path part (`parts/inputs/picker.rs` `Takes`), the part's own extensions else its field's (`FieldFacts.extensions`, `hidden`). Refusal word `fileTypeRefused` ("{field} takes {extensions} files, not {name}"), in the translations of a project with such a field. A field or part without extensions takes any file, hidden ones too, as before. `hidden` reaches the dialogs that can show hidden files: macOS (`with invisibles`) and Windows (FOS_FORCESHOWHIDDEN); zenity, kdialog and the portal cannot. Built in Go, C, C++ and Rust (the everything fixture's `booklet` and `scan` name extensions); C# runtime tests pass, its generated build not run (stale local native libraries).

Decided 2026-11-19: "folder part's Extensions can't come off! its needed for better ux!". A folder part's extensions go to the folder dialog, which shows those files while a folder is chosen where it can (the portal's `filters` with `directory`, zenity's `--file-filter` with `--directory`); Windows' folder picker and kdialog show folders alone, macOS's `choose folder` shows every file (tests `desktop_host.rs` `a_folder_dialog_shows_the_files_of_its_extensions_where_it_can`, `inputs_folder.rs` `its_extensions_go_to_the_folder_dialog`).
5. Web apps: the button opens the browser's own picker and the chosen files go to the program. BUILT 2026-11-19, as the user put it: "if an app targets a web(server) app I think it should be a filestore (on the 'webservice') for a upload target... but in design it should be the same thing... and I think this means the 'folder' option/picker is of less use, unless it picks a filestore on the webserver/-service?!". Tests: each runtime's files test, the Go shell test, Clarity.UI `inputs_file.rs` and `inputs_folder.rs`; the everything fixture builds on the web in Rust and Go.

## Decisions
- 2026-10-18: `image` kept in the database or, with `store name`, as a file in a file store named by the SHA-256 of its bytes; files in a store are never deleted (X2).
- 2026-10-18: reading records never carries pictures; the screen fetches each on its own (X2).
- 2026-10-18: code reaches files only in the project's file stores, written like `find`; a path leaving the store is refused (X2). No reason was recorded; lifted 2026-11-14 for folders that are no store (below).
- 2026-10-29: copying a picture or file between records works between the database and a store; a file of a store stays linked only in the same store (X2).
- 2026-10-29: a store's folder chosen while the program runs is a setting of type `folder`, not a click target (X2); see [settings-secrets](settings-secrets.md).
- 2026-11-12: a file store reads its folder setting as the running handler holds it; see [settings-secrets](settings-secrets.md).
- 2026-11-14: an empty list of files is written as any empty list (`let found: list<file> = []`), on every stack (`crates/clarity-gen/tests/gen/files.rs`). A table edits a folder cell: the path typed, and a button in the cell opens the folder picker (`CellKind::Folder`, `runtimes/rust-ui/tests/data/table_folder.rs`); every stack's field facts say `folder`.
- 2026-11-14: a folder that is no store is just a folder code reads and writes: `files f in folder category.folder`, `write t to folder category.folder "a.md"`, reaching the runtime as the store `folder:` and its path. A `folder` field may be in any entity now (it was settings only). A folder field says its files with `extensions "*.md *.csv"` (`"*.*"` alone: any file) and whether hidden files count with `hidden`; code lists only those and writes no other (`crates/clarity-spec/src/files.rs`, conformance `folders`, `folderWrites`). The user's words on why stores exist: "That feature is designed to have one SPECIAL place to look for files in the app so a USER doesnt make MISTAKES. That was the only reason. calculated from the APPs working directory!!!", and "there is one other thing why you made the store a thing, and that is file types and file-extentions! a folder(filebrowser) does need a way to know which extentions is looked for, or are allowed to write!". On folders: "if a folder isnt marked as a store, it's just a folder where an app can read and right". On `*.*`: "if that is set, you cannot add other extentions"; hidden: "I rather have the hidden as a boolean option added". `filestore` stays as it is ("keep it filestore").
- 2026-11-23: a relative file store and a relative folder setting (its default, or a relative folder the person typed) are in the program's data folder, found while it runs, exactly as a relative SQLite database is; nothing of the build machine is written into generated code. The generator writes a relative store as `data:<program>/<folder's name>` (`clarity_project::build_settings`, `store_kept`); each runtime finds the data folder (CLARITY_DATA, else the person's folder for application data under the program's name, else where the program runs) and the store in it: R `data_folder::folder`, `data_folder::store` (`runtimes/rust/src/data_folder.rs`), Go `DataFolder`, `DataFolderStore` (`data_folder.go`), C# `DataFolder.Folder`, `DataFolder.Store` (`Store.cs`), C `clarity_data_folder`, `clarity_data_folder_store` (`store.c`), C++ `data_folder`, `data_folder_store` (`store.cpp`); a folder setting's relative folder goes through `store_folder_in` with the data folder in place of the settings folder. `env:NAME` unset never stops the program: the store says so where it is used, and a database at it stops the start with the same words, Clarity's `variableNotSet` ("The environment variable {variable} must be set"); code listing an empty folder says `noFolderChosen` ("No folder was chosen"); both are in `RUNTIME_ERROR_KEYS`, in every example's and test project's language files. Pinned by `conformance/data-folder.json` (`folders`, `stores`) and `conformance/settings.json` (`folders`, now `dataFolder`), read by R, Go, C, C++, C#. Clarity's Run names in CLARITY_DATA the folder of the first own SQLite database, else of the first relative file store (`clarity_project::data_folder`). User: "hard coded folders or files are a problem when the examples run on a other environment", "check all examples for errors like pointing to a folder and not having that set in a setting".

- 2026-11-23: a relative store keeps its whole path from the project's data folder (the folder of its own SQLite database, else the project's folder): `data/old/photos` beside `data/shop.db` is `data:<program>/old/photos`, so two stores share a folder only when they name the same one; a relative store outside the data folder is refused by the project file check (`store_outside_data`); without a database Run's CLARITY_DATA is the project's folder (`data_root`, `store_kept`, `data_folder` in crates/clarity-project/src/lib.rs; test `settings::a_file_store_keeps_its_whole_path_from_the_data_folder`). Replaces the folder's last name only, which let `data/photos` and `old/photos` meet. User: "why is the predefined name needed?", "yes, keep the whole path", "Yes, do that".
