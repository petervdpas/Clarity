## Design (2026-11-22)

The user, 2026-11-22, asked whether migrations are "supposed to be done by rust from within clarity (ide or subprocess)", then: "clarity has its own migration tool (written in rust) like dotnet migrate (clarity migrate) that is self reliant", "it's included (optional) with an clarity made app!", and on what an app does with a database that is behind: "refuse to start, saying the db..."; without the tool included, whoever deploys it migrates with Clarity: "yes".

What it is
- One migration tool, in Rust, Clarity's own: it applies a project's steps to a database of every kind Clarity owns (SQLite, PostgreSQL, MySQL, SQL Server), backing up first where it can, recording the steps in `clarity_schema` as today. Clarity uses the same tool: the IDE, `clarity migrate` on the command line, or started as a subprocess.
- Self-reliant: it runs without Clarity installed. An app made with Clarity can include it, an option of the project (off unless asked), with the app's steps, so whoever installs the app migrates its database without Clarity.
- The generated program does not migrate. At start, before any window, it compares the steps its database has (`clarity_schema`) with the steps it was made with; a database behind or ahead stops it, with one line on the console in English, not from the translations (the user, 2026-11-22: "the rule is true, but this should stop the app from running and show a console line reason... in english"): `The database main needs migrating: run clarity-migrate` or `The database main belongs to a newer version of this app`, and it exits with 1. Without the tool, whoever deploys the app migrates with Clarity.
- The migration code of the five runtimes (Rust `migrate_source`, Go `MigrateSource`, C `clarity_migrate`, C++ `migrate_source`, C# `MigrateSource`) goes; each keeps only the check at start. Clarity stays a transpiler: the program is plain code on its stack's runtime, and the tool is one Rust program beside it, not a library under it.

## Decisions
- 2026-10-16: migrations built in for every owned source; a rename is a designer edit with a known intent, so no data is lost by guessing (DESIGN 1.3).
- 2026-10-17: numbered steps and no snapshot; replaying them gives the schema, no `schema.lock` (D1b).
- 2026-10-17: steps do not depend on a database; each runtime writes its own dialect, so one project migrates SQLite and PostgreSQL alike (DESIGN 1.3).
- Renames are suggested when a field goes and one of the same type comes, and taken only when the person picks them, never applied by guess (DESIGN 1.3; LANGUAGE.md section 4).
- 2026-10-29: an integer field that becomes a duration is proposed as a rename (X2).
- 2026-11-12: `add version Entity` and `version` in `add entity`; see [row-versions](row-versions.md).
- Before applying steps to a SQLite database with a schema, every runtime backs up first; see [backups](backups.md).
- 2026-11-23: one way to write a step and one way to rename. User: "the must be only one way and 'ide/agents OR WHATEVER' can hook into it!!!". A step never guesses a rename: the IDE's suggestions start unticked, `clarity migrate` lists them and takes only the ones named with `--rename` (`--no-renames` is gone). Every front end refuses a project with errors and a change that can lose data nobody allowed (the agents' `allowDataLoss`), titles a step `Step N` by default, and says the same when nothing is pending. The IDE's renames write the migration step as the agents' do, so the IDE no longer keeps value renames in memory until the next step.
