- C# writes a record given to `pdf of Report with ...` with .NET's default JSON (PascalCase names, decimals as numbers, enums as integers): `crates/clarity-gen/src/csharp/logic.rs:1204` -> `runtimes/csharp/Clarity.Runtime/PartValues.cs:28`; the same record set on a part goes through `WireJson` (`OpenWindow.cs:38`). ## Decisions
- 2026-11-12, after sign-in work broke tests on five stacks found only at the end. User: "If modules arent modular enough TDD doesnt work!!!! you're not able to have enough overview", and, agreeing to give sign-in one module per layer before building its providers: "yes, do that first... and that needs to happen for every specialized (modular) piece in the ecosystem!!!"
- The rule: a specialized piece (sign-in, formats, row versions, audio, a part family, ...) lives in one module per layer, each with its own tests, and logic every stack shares lives once:

| Layer | Where the piece lives |
|---|---|
| Spec | its own module for model and helpers, a checker module (`check/<piece>.rs`), a template module when New window makes it (`templates/<piece>.rs`) |
| Generators | the piece's emitting per stack in its own module, beside the stack's others |
| Shared runtime core | only for a heavy, specialized piece a program carries when it uses it (as Clarity.Auth, Clarity.Formats): its decisions once, in a Rust crate with a C interface. A program's ordinary work stays in each stack's runtime, in its own language, held equal by conformance cases (2026-11-22: Clarity is a transpiler first) |
| Clarity.UI | its own module of the window host and window stack, beside its parts |
| IDE | its own component and a TypeScript helper with node tests |
| Docs | its manual page (the manual holds the whole language), a conformance file where stacks must agree |

- A move keeps behaviour as it is and runs the module's tests before and after; a new feature of the piece then goes into its modules only.
- The rule of the order (the user, 2026-11-12, asked "is that the right order?" and chose "yes, rewrite the order"): a piece moves just before it is built on, never in one pass over everything; first what breaks across stacks, then what the next work touches. The order is Design, steps 1-5.
- 2026-11-12, on Clarity.UI's seven files over 1,000 lines. User: "yes, add them to the plan"
- 2026-11-21, the value rules for phase 2 (the open question on value semantics), the user's choices: comparing with an empty value, "Empty is smallest" (an empty value comes before every value, as Rust, Go, C, C++ do; C# changes); decimal division, "28 significant digits" (as Rust and C#; Go, C, C++ change); divide by zero and whole-number overflow, "Value error, handler stops" (the window says what went wrong, nothing the handler did is kept, as div and mod by zero do); empty values in order, "First, everywhere" (tables, `find ... order by` with NULLS FIRST on every database, comparisons). Each pinned by a conformance file every stack runs.
- 2026-11-22, phase 5: no shared runtime core under the programs. The user, after first picking "One Rust core, every program" on my recommendation and then asking the options again: "I cannot actually oversee the implications", "clarity is a transpiler mainly, right?", "that (transpiler) is the first idea for creating Clarity! To me it now feels like you undermining this with suggesting the one core option!!". So a program's ordinary work (row versions and undo, backups, migrations, the query builder, table order) stays in each stack's runtime, in its own language, held equal by conformance cases; a native Rust library only for a heavy, specialized piece a program carries when it uses it (Clarity.UI's drawing, PDF, audio, video, formats, sign-in). This narrows the rule's "Shared runtime core" row below to such pieces.
- 2026-11-21, after the map: the refactor in phases (above). User: "My gut feeling says we need a big refactor!", "yes, propose it in phases when the map is done", then "yes, start with phase 0".
